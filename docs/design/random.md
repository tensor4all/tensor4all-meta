# Random numbers in tenferro: counter-based, generated on the device

**Status:** Proposed (2026-11-22).
**Scope:** [tenferro-rs](https://github.com/tensor4all/tenferro-rs) (a new `tenferro-random` crate, new primitives in the core vocabulary, CPU and CUDA kernels), [t4a-cuda-kernels](https://github.com/tensor4all/t4a-cuda-kernels) (the CUDA sources), and the downstream users in [tensor4all-rs](https://github.com/tensor4all/tensor4all-rs).
**Tracking issue:** to be opened in tenferro-rs; it succeeds [tenferro-rs#989](https://github.com/tensor4all/tenferro-rs/issues/989) (graph-level RNG key semantics, closed as not planned until random ops were requested).
**Checked against:** tenferro-rs `main` `3b3bb6df`, t4a-cuda-kernels `main` `639f60d`, tenferro-sci-rs `main` `f574bde`, tensor4all-rs `main` (2026-11-22). Findings come from reading code; nothing was built.

## 1. Decisions

1. Random numbers live **in tenferro-rs**, not in tenferro-sci-rs.
2. Samples are **generated by kernels on the tensor's device** (CUDA first, CPU
   as the reference). There is no host generation followed by an upload.
3. The generator is **counter-based and stateless**: a sample is a pure
   function of `(algorithm, key, element index)`. Randomness is never hidden
   state.
4. The **algorithm is replaceable**: it is a static attribute of every random
   operation, identified by name, and new algorithms are added behind one trait
   without touching the operations or the public API.
5. **No unsigned dtype is added.** Keys are `I32` tensors read as `u32` bit
   patterns, and the operations produce floating-point or signed-integer
   samples directly.

## 2. What exists today

- tenferro-rs has no random tensor API. The workspace declares `rand = "0.8"`,
  but no crate uses it (the `rand` in `Cargo.lock` comes from `omeco`, which
  uses it inside TreeSA).
- The production code of tenferro-rs draws no random numbers itself. The only
  indirect use is contraction-order search through omeco's TreeSA.
- Eight test, benchmark and example files in `tenferro-linalg` and
  `tenferro-einsum` carry their own small generators (SplitMix64 and similar).
- The dtypes are `F32, F64, I32, I64, Bool, C32, C64`. There are no unsigned
  integers and no bitwise, shift or bitcast primitives, so a counter-based
  generator cannot be composed from the existing primitives.
- `tenferro_gpu::cuda::raw` is public, but it borrows streams and tensors and
  allocates outputs; loading and launching an external NVRTC/PTX module is
  designed ([`gpu-extension-api.md`](https://github.com/tensor4all/tenferro-rs/blob/main/docs/design/gpu-extension-api.md),
  tenferro-rs#1597) but not yet public (tenferro-rs#2694). tenferro-gpu
  compiles its own kernels with NVRTC from sources in t4a-cuda-kernels.
- tensor4all-rs uses `rand` 0.9, `rand_chacha` 0.9 and `rand_distr` 0.5 in
  most crates. Random initial tensors (`IdxTensor::random`,
  `random_tt`, `randomized_svd` and its range finders) are drawn on the host
  and uploaded. Its complex normal draws real and imaginary parts from N(0, 1)
  each.

## 3. Why tenferro-rs and not tenferro-sci-rs

[`tenferro-sci.md`](./tenferro-sci.md) keeps out of tenferro-rs any family
that can be written with tenferro's public API. Random numbers are an
exception, for three reasons:

- **Device generation needs the core.** A sample must be produced by a kernel
  on the device. Until the public GPU window (tenferro-rs#2694) lets an
  external crate launch its own kernels, only tenferro-cpu and tenferro-gpu can
  host those kernels; and a traced program can only contain a random operation
  if the operation is in the primitive vocabulary.
- **Other families in tenferro-rs will need it.** Randomized range finders
  and randomized SVD belong next to `tenferro-linalg`; today they live in
  tensor4all-rs and draw on the host.
- **The tests share it.** The eight hand-written generators become one.

This matches JAX and PyTorch, where random numbers are part of the core.

## 4. Model

### 4.1 Keys

A key is a device-resident tensor of dtype `I32` and shape `[2]` (a batch of
keys has shape `[..., 2]`), read as two `u32` words. Both built-in algorithms
take a 64-bit key, so one representation serves both.

- A key never changes. Using the same key twice gives the same samples, on
  purpose.
- New randomness comes from deriving keys: `split(key, n)` gives `n`
  independent keys, `fold_in(key, data)` mixes a 32-bit value into a key.
- Keys are runtime inputs. They are never part of a cache key or a program
  identity, so a traced program compiled once runs with any key.
- A convenience `Generator` holds a key and a counter and derives a fresh key
  per draw. It is an ordinary value the caller owns; there is no global RNG
  state.

### 4.2 Samples

A random operation fills the output so that element `i` (its **logical
column-major index**, independent of the storage layout) is computed from the
generator's block at counter `i / words_per_sample`. The result does not depend
on the thread count, the launch configuration, the device or the storage
layout.

| Operation | Output dtypes | Transform |
| --- | --- | --- |
| uniform on [0, 1) | F32, F64, C32, C64 | 23 or 52 random mantissa bits; exact |
| uniform on [lo, hi) | F32, F64 | from [0, 1) by `lo + (hi − lo)·u` |
| standard normal | F32, F64, C32, C64 | Box–Muller; complex draws have E\|z\|² = 1 (real and imaginary parts N(0, 1/2)), as in JAX and PyTorch |
| integers in [lo, hi) | I32, I64 | 64-bit multiply (Lemire) without rejection; bias at most (hi − lo)/2⁶⁴, documented |

Every transform consumes a fixed number of bits per sample, so a sample is
still a pure function of its index. Rejection sampling and the ziggurat method
are not used for this reason.

Like JAX, tenferro does not promise sequential equivalence: drawing `n`
samples at once need not equal `n` draws of one sample.

### 4.3 Replaceable algorithms

```rust
/// A counter-based generator: `block` is a pure function of its arguments.
pub trait CounterRng: Copy + Send + Sync + 'static {
    /// Stable name; part of every random operation's identity.
    const NAME: &'static str;
    /// `u32` words produced per block.
    const WORDS_PER_BLOCK: usize;
    /// Reference implementation, used by the CPU kernels.
    fn block(key: [u32; 2], counter: u64, out: &mut [u32]);
    fn seed(seed: u64) -> [u32; 2];
    fn split(key: [u32; 2], n: usize, out: &mut [[u32; 2]]);
    fn fold_in(key: [u32; 2], data: u32) -> [u32; 2];
}
```

- Every random operation carries an `RngAlgorithm` attribute. The built-in
  algorithms are `threefry2x32-20` (the block function of JAX's default) and
  `philox4x32-10` (Random123; the family used by cuRAND and PyTorch on CUDA).
- Each algorithm has a Rust reference implementation in tenferro-rs and a
  CUDA device function in t4a-cuda-kernels. The CUDA kernel is one template per
  operation into which the algorithm's block function is inserted; NVRTC
  modules are cached per (algorithm, operation, dtype).
- Adding an algorithm means adding both halves and their known-answer tests;
  no operation or public API changes.
- The output of an algorithm, once released, is frozen. A change in output is
  a new algorithm with a new name.
- Registering algorithms from outside tenferro waits for the public GPU window
  (tenferro-rs#2694).
- A sequential host generator (ChaCha and other `rand_core::RngCore` types) is
  not a backend of these operations: it cannot run per element on a device.

### 4.4 Reproducibility contract

| Same algorithm, key, shape and dtype | Guarantee |
| --- | --- |
| raw bits, uniform, integers | bit-identical on CPU and CUDA, for any thread count and layout, across tenferro versions |
| normal | bit-identical on the same device and backend; CPU and CUDA agree within a documented ulp bound (they use different `log`, `sin`, `cos`) |

### 4.5 Primitives

New entries in the core vocabulary (names to be settled in the feature
issue):

| Primitive | Inputs | Output | Static attributes |
| --- | --- | --- | --- |
| `RngSeed` | seed (`I64[]`) | key `I32[2]` | algorithm |
| `RngSplit` | key `I32[2]` | keys `I32[n, 2]` | algorithm, `n` |
| `RngFoldIn` | key `I32[2]`, data `I32[]` | key `I32[2]` | algorithm |
| `RngUniform` | key | sample tensor | algorithm, dtype, shape |
| `RngNormal` | key | sample tensor | algorithm, dtype, shape |
| `RngInteger` | key, `lo`, `hi` | sample tensor | algorithm, dtype, shape |

- **AD:** none of these is differentiable; keys and bounds receive no
  cotangent. Samples flow into later operations as ordinary primal values.
- **Identity:** algorithm, dtype and shape are part of the program and cache
  identity; key values are not.
- **Backends:** CPU is the reference and CUDA is required before release. XLA
  reports `Unsupported` at first, then lowers by expanding the block function
  into StableHLO `ui32` arithmetic. StableHLO `rng_bit_generator` is not used,
  because its bit stream is implementation-defined. ROCm and Metal follow the
  backend designs ([`rocm-backend.md`](./rocm-backend.md),
  [`metal-backend.md`](./metal-backend.md)).
- **Fusion:** at first each operation is its own kernel; later the uniform and
  normal operations can become producers in the elementwise fusion.

### 4.6 Crates

- `tenferro-random-core` (tenferro-rs, no dependencies): `CounterRng`, the
  built-in algorithms and the bits-to-sample transforms as scalar Rust. The
  CPU kernels call it; any Rust code can use it.
- t4a-cuda-kernels: the CUDA block functions and operation templates, with
  the same known-answer tests.
- The primitives in `tenferro-core-ops` and `tenferro-internal-ops`, kernels in
  `tenferro-cpu` and `tenferro-gpu`.
- `tenferro-random`: the public API on the concrete, eager and traced layers,
  following the API grammar of tenferro-rs#2552. It is a first-class operation
  crate like `tenferro-einsum`; there is no `tenferro::random` facade path. It
  sits before `tenferro-linalg` in the publication order, so linalg can use it.

## 5. Tests

Tests are small and fast, with fixed keys and exact assertions.

- Known-answer vectors from Random123 for both algorithms, and the outputs of
  JAX's `threefry_2x32` for the Threefry block, split and fold-in, generated by
  a recorded script with the JAX version noted. The sample layout is
  tenferro's own (column-major), so whole arrays are not compared with JAX.
- Each operation on at most eight elements against hard-coded values, on CPU.
- CPU against CUDA, bit for bit, for keys, bits, uniform and integers on one
  small shape; normal within its documented bound.
- Properties: the same key gives the same samples, split keys give different
  samples, a key is not modified, and generation is independent of the layout.
- No statistical tests in the test suite: they are slow and probabilistic.

## 6. Plan

Each step is one pull request unless noted.

0. This document, and a feature issue in tenferro-rs that carries the API,
   the non-goals and the acceptance criteria.
1. `tenferro-random-core`: `CounterRng`, Threefry2x32-20, Philox4x32-10, seed,
   split, fold-in, the transforms, known-answer tests.
2. t4a-cuda-kernels: the CUDA block functions and operation templates, with
   the same known-answer vectors; release.
3. The primitives and CPU kernels: core-ops, internal-ops (no AD rules),
   runtime (shape inference, identity), tenferro-cpu.
4. The CUDA kernels in tenferro-gpu, with capability reporting and the CPU
   against CUDA test. Steps 3 and 4 ship in the same release: the operations
   are never released without CUDA.
5. `tenferro-random`: keys, `Generator`, uniform, normal and integers on the
   concrete, eager and traced layers; guide and `llms.txt`.
6. Replace the eight hand-written generators in tests and benchmarks, and
   remove the unused `rand` workspace dependency.
7. Elementwise fusion of the samplers and the XLA lowering.
8. External algorithms, after tenferro-rs#2694.
9. tensor4all-rs: move random initial tensors and randomized range finders to
   tenferro (decided separately; the complex normal convention changes).

## 7. Open questions

- The default algorithm: `threefry2x32-20` (same block function as JAX) or
  `philox4x32-10` (fewer rounds per bit on GPUs).
- Whether `RngSeed` is a primitive or the seed is a kernel argument of a
  key-creating call outside traced programs.
- The ulp bound promised for normal samples between CPU and CUDA.

## Non-goals

- Hidden or global RNG state, and NumPy-style sequential generators.
- Hardware random number generators.
- Statistical distributions beyond uniform, normal and integers in the first
  release (they can be built on these).
- A `rand_core` backend for the operations.
