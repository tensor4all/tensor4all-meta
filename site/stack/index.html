Stack overview

The tensor4all Rust stack

Rust libraries for scientific computing that grew out of tensor networks. At the top are quantics tensor trains, tensor cross interpolation and tree tensor networks; underneath are a tensor runtime with automatic differentiation, tensor contraction, batched linear algebra and the thread model they all share. Every layer can be used on its own.

★ Flagship projects

Two projects carry the stack. Start with one of them; the rest of this page shows what they stand on.

★ Flagship · algorithms

tensor4all-rs

Tensor network algorithms in Rust, ported from the tensor4all Julia ecosystem and grown beyond it.

  • Quantics TCI: learn a QTT from an expensive function, then integrate or evaluate it
  • QTT operators: Fourier transform, shift, flip, affine maps
  • Tree tensor networks: contraction, DMRG, TDVP, linear solve
  • Adaptive patching, ITensors.jl compatible HDF5, C API, Julia and Python frontends
User guide → Stack guide for users →
★ Flagship · tensor runtime

tenferro-rs

A Rust-native tensor runtime with opt-in automatic differentiation for scientific workloads.

  • Typed and dynamic dense tensors, einsum, linear algebra, FFT
  • Eager AD with PyTorch-style backward(); traced AD with JAX-style VJP, JVP and Hessian vector products
  • CPU and CUDA, with an experimental XLA path
  • One explicit engine carries the thread pool, plan cache and buffers: no global state

The layer map

Each layer depends only on layers below it. Bands are layers, named by their role; boxes are libraries, and each name links to its GitHub repository. ★ marks the two flagship projects. hataori sits beside the stack: it does not compute anything itself, it splits the machine into MPI ranks and thread domains and lends them to the layers that do.

The layers in brief

  • Frontends. Rust programs use tensor4all-rs directly. Tensor4all.jl is a Julia frontend over the C API, maintained on a best effort basis for light use and teaching. Python bindings (tensor4all-py) live in the tensor4all-rs repository.
  • Algorithms. ★ tensor4all-rs holds the algorithms: tensor trains, TCI, quantics grids and operators, tree tensor networks, patching, HDF5 I/O. It keeps two stacks on purpose (a TT and TCI stack and a network stack) with an explicit bridge between them. Grid and coordinate conversion lives in the standalone quanticsgrids-rs.
  • Tensor runtime. ★ tenferro-rs is the tensor runtime: typed and dynamic tensors, eager and traced automatic differentiation, CPU and CUDA backends and an experimental XLA path. tensor4all-rs reaches it through one adapter crate. computegraph-rs supplies the graph IR that traced AD builds on.
  • Kernel providers. Tensor-free numerical libraries that tenferro calls: cpueinsum for N-ary einsum, tcontract for binary contraction over arbitrary strides, and tlinalg for batched factorizations. They take borrowed strided views and an explicit execution token, so they are usable on their own, including from C.
  • Foundation. strided-rs defines the strided view types every layer above passes around. threadteam-rs owns the CPU threads: it is the only place in the stack where parallel tasks start. Dense arithmetic comes from tensor4all's fork of faer, published as t4a-faer, and optionally from a vendor BLAS and LAPACK.
  • Beside the stack. hataori-rs provides data-parallel map and pmap over serial, Rayon, MPI and hybrid execution, for the outer level of a study: parameter scans, momenta, independent patches.

Beyond tensor networks

The stack started as the backend of tensor network algorithms, and its lower layers are now general tools for dense numerical work in Rust. None of them requires tenferro or tensor4all-rs.

  • Linear algebra. t4a-faer is a pure Rust dense and sparse linear algebra library. It is validated nightly against LAPACK 3.12's own test suites, its steady-state calls are tested to allocate nothing, and its results are bitwise reproducible at a fixed thread count. In the published comparison on a Zen 5 host it is faster than both MKL and OpenBLAS in most of the measured cases. Migration guides cover LAPACK, Eigen, NumPy and SciPy users.
  • Tensor contraction. tcontract contracts tensors in any index order without transposing them first, and speaks TAPP, the community C interface for tensor products, so C, C++ and Fortran codes can call it.
  • Batched factorizations. tlinalg runs SVD, QR, LU, Cholesky and eigensolvers over whole batches of matrices and decides how to spread them over threads.
  • Threads that cooperate. threadteam gives a caller one pool to hand down, so a library call never competes with the OpenMP, MPI or Julia threads of the host program.

First-principles, quantum chemistry and HPC developers: the host code section of the backend guide shows how to call these libraries from an existing code, and the essay Why rewrite first-principles codes in Rust argues the case. Issues with your typical shapes are very welcome.

Three ideas that run through every layer

  1. Explicit execution. No library in the stack starts a hidden global thread pool or changes behavior through environment variables. The caller builds one thread pool (a threadteam Pool) and passes a token for it down; tenferro bundles that pool with its scratch memory and plan cache in an engine. This is what lets an MPI program, a Julia session and a Rust test share one machine predictably.
  2. Tensor-free providers. The numerical kernels (tcontract, tlinalg) do not know about tensor types. They take borrowed strided views. The host above them owns allocation, dtype dispatch and placement. That keeps them small, testable on plain buffers and reusable from other codes.
  3. One shared vocabulary. All CPU layers exchange strided-rs views and threadteam tokens. A view made by tenferro can be handed to tcontract or tlinalg without conversion, which is why the whole stack resolves to the same strided-rs and threadteam releases.

Join the community

tensor4all is open to new developers, and AI assisted contributions are welcome. The rules that hold in every Rust repository are in the contribution rules; each repository adds its local facts in AGENTS.md and its contributing guide. Good first contributions are benchmark cases from real applications, kernels for hardware we have not tuned for, and bindings for other languages.
